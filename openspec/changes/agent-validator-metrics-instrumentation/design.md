## Delivery transaction and scheduling

Use a dedicated delivery client and synchronized, durable per-run delivery state. Keep step executors in `internal/exec`; model types remain independent of executors and engine. The existing void audit logger is useful for events but cannot itself authorize acknowledgment because it returns no durable persistence result.

1. Persist launch attribution before launch. After any child outcome, attempt delivery using a bounded cleanup context independent of a canceled child context.
2. Negotiate capabilities/protocol v1 and measurement v1. Export with explicit project/configuration, `--consumer agent-runner --context <id> --protocol-version 1 --measurement-version 1`, and a bounded `--max-records` within advertised limits.
3. Validate the whole response and each accepted record's closed envelope/payload, identities, scope, version, numeric limits, and RFC 8785 SHA-256 digest. Reject duplicate JSON keys. Verify the original complete record excluding only its top-level `digest`; retain it unchanged under a separate Runner attribution wrapper.
4. Commit verified revisions, exact batch metadata, and opaque receipt to a durable journal/snapshot. Persist the updated v4 artifact before acknowledgment. The implementation must sync written files, atomically replace snapshots, and sync affected directories (including newly created durable directories); any failed durability operation prevents acknowledgment.
5. Acknowledge the whole exact receipt, with dispositions recorded for each revision in its manifest; there is no acknowledgment of only the valid subset of a receipt. Acknowledge only after both durable incorporation and artifact publication succeed. Save acknowledgment disposition durably. Lost acknowledgment responses are retried idempotently. Re-export and repeat to drain bounded batches, stopping with explicit pending state on retry exhaustion or nonretryable errors.

An invalid or otherwise unacknowledgeable batch stops draining that context for the current pass with explicit blocked delivery; later pending revisions remain undelivered. Report a safe error code and the blocking record identity only when that identity is safely established. Recovery returns non-success and requires correction/restoration of the evidence or a compatible consumer before it can proceed. Runner never skips or automatically discards the blocking batch. Any operator-initiated Validator discard is a separate explicit action and leaves a permanent delivery gap.

A journal is the recovery authority for imported evidence and outstanding receipts; `run-metrics.json` is the supported downstream projection. Recovery reconstructs and durably republishes the artifact before acknowledging when a crash separates these writes. Serialize recovery and normal metrics updates using the run's exclusive ownership/locking boundary so they cannot overwrite one another. Preserve corrupt state and report a gap; do not acknowledge against unverified reconstructed history.

Replay stored contexts on workflow resume before launching new measured work, and make one bounded final delivery pass at run shutdown. Also provide `agent-runner metrics recover <run-id>` using existing run/project resolution and lock semantics so interrupted or completed runs can retry delivery without executing workflow steps. Recovery updates original records/rollups, creates no new measured work or execution session, and refuses concurrent writers. It returns a non-success status with safe actionable diagnostics if unresolved delivery remains. No daemon, unbounded wait, validation rerun, clean, or automatic discard is needed. Retry only explicitly retryable errors; cap attempts and elapsed time, retaining remaining work for later recovery.

Use `metrics pending` only for bounded operational discovery where needed. An unknown context cannot acquire the recovery caller's attribution and must remain unresolved and unacknowledged. Original configuration/storage relocation requires restoration or a separately authorized migration. A matching consumer/context at a different `store_id` must not silently replace the original store association.

## Measurement identity, revisions, and completeness

Deduplicate producer records by producer/store identity, record type, and producer record ID across all recovery sessions. Revision and measurement version identify complete immutable replacements; preserve the original Runner context mapping. Identical replay is idempotent, newer revisions replace the current head, stale revisions never overwrite it, and same-revision conflicting digests prevent numeric contribution until resolved. Keep enough revision/digest/receipt evidence in the journal to verify outstanding or overlapping receipts after selecting a newer head.

Only support measurement v1 initially. An unsupported actual current head must never select an older compatible head for aggregation. Protocol, measurement, native measurement, outer artifact, and aggregate interpretation are explicitly versioned independently. Reject undeclared fields, including optional unknown fields; do not create an opaque extension bag.

Reconcile current invocation `attempt_ids`, lifecycle, `zero_dispatch`, imported attempt heads, batch coverage at its generation, and explicit delivery gaps. A terminal invocation and `scope_complete` alone do not establish delivery completeness. Batches can separate invocation and attempts; there is no `context_records` field. A finalized invocation with `zero_dispatch: true` and an empty attempt set establishes zero dispatch, while missing, prepared-only, discarded, or incomplete evidence does not.

Overlapping receipts need no special client-owned pin tracking: any producer-confirmed disposition releases the relevant revision. Keep stale receipts retryable, but do not require a separately acknowledged abandoned receipt to prove delivery once its exact revisions have confirmed dispositions. A discarded revision remains a gap even after a later acknowledgment attempt.
