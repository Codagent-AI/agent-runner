# Decisions

| Step | Decision | Alternatives considered | Decision-bearing |
|------|----------|-------------------------|------------------|
| propose | Verdict: go. The problem is concrete (sub-agent abort under headless) and the global-only setting is too coarse. | No-go (rely on prompt instructions or global setting) | yes |
| propose | Expose the choice as a step field `autonomous_backend` that reuses the user-setting values `headless` / `interactive` / `interactive-claude`. | New `mode: autonomous-interactive` value; boolean `interactive_backend`; agent-profile field | yes |
| propose | Precedence: step field > user setting > headless default. Capture, no-TTY fallback, and external-user overrides still win. | Step field overrides the safety rules too | yes |
| propose | Keep the no-TTY fallback to headless (with warning) for steps that request interactive. | Fail the step when interactive is requested without a TTY | yes (superseded by PR-001 below) |
| propose | Reject `autonomous_backend: interactive`/`interactive-claude` combined with `capture` at load time, and reject the field on non-agent steps and explicit `mode: interactive` steps. | Accept silently and force headless at runtime | no |
| propose | The field applies only to the step it is written on; no cascade into group, loop, or sub-workflow children. | Inherit into nested steps | no |
| propose | Out of scope: editing the orchestrated implement-change workflow, which lives in open PR #209. | Include the YAML adoption in this change | no |
| proposal-review | PR-001 (significant) **applied**: an explicit step-level `interactive` (or `interactive-claude` resolving to Claude) is a requirement. With no TTY or in external-user mode the step fails before launch with a clear reason instead of downgrading to headless. Steps that only inherit the global setting keep today's fallback. Proposal updated in What Changes, Capabilities (adds `external-user-mode`), Technical Approach, Out of Scope, and Impact. | Keep preference semantics and revise the correctness claims (the reviewer's alternative). Rejected because a silent downgrade brings back the exact sub-agent abort the field exists to prevent. | yes |
| proposal-review | Not treated as a direction-level stop. The failure applies only to the new opt-in field, so no existing workflow or persisted format changes. It doesn't contradict the issue, and it follows the precedent that interactive shell and UI steps fail in external-user mode. Consequence recorded in Impact: unattended runners without a TTY can't run steps that adopt the field. | Stop for a human decision | yes |
| spec | If a step sets `autonomous_backend`, omits `mode`, and its profile `default_mode` makes it interactive at execution time, the step fails before launch. This holds for any value, `headless` included. | Ignore the field when the mode resolves to interactive; fail only for interactive values | no |
| spec | The `autonomous_backend` field is rejected at load time on group and loop steps as well as shell, script, UI, and sub-workflow steps. | Allow it on group or loop steps as a default for their children (contradicts the no-inheritance decision) | no |
| spec | A missing-TTY or external-user failure caused by a step-required backend is an ordinary step failure, so `continue_on_failure` and the step's other existing failure handling apply. | A hard run abort that bypasses failure handling | no |
| spec | `interactive-claude` set on a step whose resolved CLI isn't Claude means headless with no failure, in every environment. This matches the existing user-setting semantics. | Treat it as an unmet requirement and fail | no |
| spec | "Autonomy system prompt enrichment for interactive backend" is left unmodified. It keys on the effective invocation context, which the new resolution requirement already covers. | Add a delta that restates it for step-level backends | no |
| design | Allowed step values are declared in `model` (`AutonomousBackendValues`), with a parity test against the `usersettings` constants. `model` stays free of service imports. | Move the type into `model` and alias it from `usersettings`; import `usersettings` from `model` | no |
| design | `resolveInvocationContext` takes the step and returns `(InvocationContext, error)`. A step-required request that cannot be met fails through `emitAgentFailure` before launch. | A separate preflight check function | no |
| design | `ResolveAgentInvocationContext` (terminal-handoff hint) keeps its signature and returns headless when resolution fails, so no terminal handoff happens for a step that will fail. | Propagate the error to dispatch | no |
| design | No new audit or run-state fields. The failure reason goes in the existing step-end `error`. | Add a backend-source audit field | no |
| test-plan | Automated wiring coverage goes into the existing testscript suite: a no-TTY run of the real binary with a stub CLI. That gives two end-to-end tests and one integration test; no new suites or jobs. | Go-level executor integration tests only; PTY-driven automated tests | no |
| test-plan | No automated end-to-end test for the TTY-present autonomous-interactive path. Unit tests cover selecting it through the `isStdinTerminal` seam, and the launch path itself is unchanged. The acceptance pass may use a PTY harness. | Add a PTY-based end-to-end test (flaky; the repo notes that synthetic PTYs can't drive some flows) | no (superseded by AR-001 below) |
| test-plan | The acceptance envelope allows a few trivial real-CLI runs in temp directories using existing local logins. The user's real settings, built-in workflows, GitHub, and the live factory are off limits. Human-only testing: none. | Stubs only; require a human terminal check | no |
| approach-review | AR-001 (medium) **applied**: added INT-002, which extends the existing direct-launch PTY workflow test (`smoke_interactive_integration_test.go`) with a step-level `autonomous_backend: interactive` overriding a `headless` setting. It asserts interactive-form args, autonomy and completion instructions, autonomous permission flags, and a successful run after control-channel completion. Also added a positive `ExecuteAgentStep` test to the design's Testing section, and updated the coverage map and envelope risk areas. | Leave it optional in acceptance (rejected: new field's success path would have no required evidence); make it a mandatory acceptance step only (rejected: an existing automated PTY harness makes it cheap and deterministic) | no |
| tasks | A single implementation task covers the whole change: model validation, resolution, docs, and every unit, INT, and E2E obligation. | Split into model, exec, and tests tasks | no |
