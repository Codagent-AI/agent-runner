## Coverage Strategy

Specifications remain the source of unit-test requirements. This plan records only additional integration, end-to-end, agent-acceptance, and exceptional human-only obligations.

The highest risks are incorrect configuration-to-execution wiring, accidental interleaving inside the built-in repository phase, state, evidence, or session leakage across repositories, unsafe resume after repository or plan drift, and divergence between execution state and the live or saved run view. Controlled integration tests cover these boundaries with real filesystems, Git worktrees, serialized state, audit streams, and embedded workflow definitions. Public-CLI end-to-end tests then prove the critical Git-backed coordination-workspace journey, process-boundary resume, and terminal presentation.

Agent acceptance uses three real temporary private GitHub repositories—one coordination workspace and two implementation repositories—real agents, real per-repository Agent Validator configurations, and real pull-request operations. These flows are intentionally required rather than replaceable with local stubs. The deterministic E2E suite uses controlled agent, Validator, and `gh` executables so ordinary CI has no credentials, network dependence, external cost, or cleanup burden.

The plan does not repeat isolated validation, parsing, interpolation, state-shape, or tree-model cases that belong in implementation-time unit tests. It does not run the workflow matrix against every supported agent CLI: one configured real agent proves the multi-repository workflow semantics, while existing adapter-specific tests retain responsibility for CLI invocation and session protocol differences. Parallel execution, cross-repository transactions, coordinated commits, and multi-repository pull requests remain out of scope and receive no coverage.

## Integration Tests

### INT-001: Workspace configuration reaches scoped execution
- Covers: Workspace repository declarations, root-only launch identity, implicit single-repository compatibility, explicit repository targets, workspace/repository dispatch, context-neutral built-in children, nested active-repository suppression, scoped built-ins and workdirs, called-agent starting boundaries, unselected repositories, checkout locking, and legacy unscoped behavior.
- Boundary: Project configuration loading and canonicalization through workflow validation, execution-context construction, scope dispatch, executor process working directories, sub-workflow composition, and called-agent workdir resolution.
- Setup: Create a temporary coordination Git worktree plus real ignored nested and sibling Git worktrees, including symlinked paths and one configured but unselected repository. Load keyed repository configuration and a matrix of workspace-scoped, repository-scoped, mixed-scope, nested, and legacy fixture workflows. Use recording process and agent-call adapters while retaining real filesystem and Git-root discovery.
- Action: Prepare and execute each workflow with ordered `repositories` values, relative and absolute step workdirs, nested repository children, context-neutral Validator/finalization children, permitted or escaping called-agent workdirs, root and subdirectory launches, overlapping concurrent selections from the same and different workspaces, a stale lock owner, and implicit standalone launches without parameters.
- Assertions: Scope-aware launch requires the workspace Git root and run storage is keyed there; canonical identities are stable; roots equal to the workspace and reserved, invalid, or duplicate declarations fail before execution; workspace work runs once; selected repositories run sequentially per fan-out boundary; separate repository leaf steps may revisit repositories; context-neutral children execute once in the caller's active context; nested repository scope does not fan out again; effective directories and scope-aware built-ins match the active scope; called children cannot start outside their active Git boundary; later filesystem access is not sandboxed; unselected repositories receive no work; global canonical-root locks make overlapping live selections fail before mutation without deadlock, report the owner, and recover stale owners; implicit standalone entry points do not expose `default`; and an unscoped workflow retains its previous single execution behavior, including outside Git.
- Execution: Add focused integration cases beside `internal/config`, `internal/runner`, and `internal/exec`; run through `go test ./internal/config ./internal/runner ./internal/exec` and the normal `make test` CI phase.

### INT-002: Planned task groups drive shipped workflow topology
- Covers: Planned task groups, authoritative parser ownership, explicit affected-repository threading, canonical workspace task paths, repository-specific numbered task loops, full and simple change topology, repository preflight after planning, independent workspace Git/PR operations, and explicit scope declarations on embedded workflows.
- Boundary: Strict `tasks.md` parsing and filesystem task discovery through normalized selection persistence, workflow interpolation, embedded workflow loading/composition, and repository-scoped loop inputs.
- Setup: Create flat implicit full-change plans, monolithic implicit simple-change plans, and grouped configured-workspace plans for OpenSpec and spec-driven changes. Include valid backend/frontend groups, duplicate or unknown owners, cross-group links, unlinked files, empty files, unsafe paths, reordered groups, compact simple-change task groups, valid backend-only remediation, an unselected remediation owner, and a selected repository with no remediation entry. Load every embedded workflow and its resolved children.
- Action: Resolve each plan, validate the affected set, construct the active repository task glob, route the structured remediation ledger, and validate the shipped `change`, `implement-change`, `simple-change`, Validator, Git, archive, acceptance, and finalization workflow graph.
- Assertions: The Go parser is authoritative and the shell validator delegates task checks to it; group heading order becomes the captured `affected_repositories` order; each configured child receives it explicitly as `repositories`; a repository-local resolver supplies the correct canonical pattern; explicit repositories see only numerically ordered owned files; implicit full changes use flat task files and implicit simple changes use monolithic `tasks.md`; invalid ownership fails before repository execution; remediation rejects unselected keys and passes only the active repository's approved entry while a missing entry is a no-op; orchestration workflows have explicit scope while approved context-neutral blocks remain intentionally unscoped; workspace planning and OpenSpec lifecycle remain outside implementation-repository containers; OpenSpec finalization includes the workspace repository; spec-driven finalization omits an unchanged workspace; simple-change finalizes implementation PRs in both project shapes; and no multi-repository workflow variants are introduced.
- Execution: Add parser/composition integration coverage under the task-group package and `workflows/`; run its focused package tests plus `go test ./workflows` and the normal `make test` CI phase.

### INT-003: Repository execution state survives process reconstruction
- Covers: Persisted repository selection and positions, deterministic resume, configuration and task-plan drift rejection, fail-fast behavior, repository capture and evidence isolation, typed captures, repository-local unnamed and named sessions, inherited workspace named sessions, repository PR outcomes, and legacy state compatibility.
- Boundary: Runner execution through `state.json` serialization, state reload into a new runner instance, nested loop/sub-workflow restoration, task-group revalidation, capture interpolation, session resolution, and audit continuation.
- Setup: Execute a two-repository fixture whose second repository fails inside a loop inside a sub-workflow after producing same-named files plus string, list, and map captures. In one variant instantiate a named lead session in workspace scope before both repositories; in another first instantiate that name independently inside each repository. Create unnamed implementor sessions in each repository. Preserve state, then construct a fresh runner for resume. Prepare variants with changed selection order, moved repository roots, removed repositories, changed task ownership, and legacy state without repository fields.
- Action: Resume each state variant and continue the valid run to completion.
- Assertions: Completed repositories are not replayed; the failed repository resumes at its deepest recorded position; later repositories remain pending until it succeeds; repository captures, evidence, and unnamed sessions restore only in their owning repository; workspace captures remain shared without reverse aggregation; a workspace-instantiated lead session remains identical across repositories while repository-first named sessions differ; `inherit` never falls back across the repository boundary; PR results remain scope-keyed; identity and task-group drift fail before spawning work; and legacy state follows the existing non-fan-out path.
- Execution: Add reconstruction integration cases beside `internal/runner` and `internal/stateio`; run through `go test ./internal/runner ./internal/stateio` and the normal `make test` CI phase.

### INT-004: Repository evidence projects consistently into run views
- Covers: Repository boundary and identity audit data, repository execution containers, live visibility and auto-follow, saved-run reconstruction, output/evidence isolation and index, repository summary drill-down, metric rollups and explicit metrics-artifact identity, repository PR detail, and ordered comma-separated breadcrumb links.
- Boundary: Persisted state plus audit and output files through audit replay, run-tree construction, live event application, selected-detail filtering, summary aggregation, hyperlink rendering, and implicit-repository flattening.
- Setup: Build complete and failed audit/state fixtures with workspace activity, two explicit repositories, a pending repository, nested loops/sub-workflows/calls, duplicate capture names, usage/cost data, safe and unsafe PR URLs, and an implicit `default` control run.
- Action: Load fixtures through historical inspection and feed the same event stream incrementally through the live model; navigate repository, nested, and summary levels.
- Assertions: Explicit repositories appear in persisted order with name-only labels; pending, active, completed, and failed statuses are correct; selected output, evidence-index entries, and metrics never include siblings; external metric records carry explicit repository fields; live auto-follow moves through the active repository ancestry and respects manual pause/jump-to-live; totals include workspace and repositories exactly once; repository detail shows only its PR; the breadcrumb keeps the workspace PR first and repository PRs in selection order; and the implicit repository remains flat with legacy audit, output, and metrics shapes.
- Execution: Extend `internal/runview/historical_integration_test.go` and live-run integration coverage; run through `go test ./internal/runview ./internal/liverun` and the normal `make test` CI phase.

## End-to-End Tests

### E2E-001: Git workspace coordinates independent repositories
- Covers: The first-slice proof, Git-backed workspace operation, contiguous built-in repository execution, repository-specific validation and Git/PR behavior, workspace-owned orchestration artifacts and PR, unselected repository protection, and shared built-in workflow semantics.
- Surface: Built `agent-runner` public CLI in headless mode using a purpose-built scope-aware workflow fixture.
- Setup: Create a real temporary Git workspace `foo` with ignored nested real Git repositories `backend`, `frontend`, and `docs`, plus a sibling-root configuration variant. Configure backend and frontend, leave docs unselected, create grouped numbered task files, and install controlled agent, `agent-validator`, and `gh` executables on an isolated `PATH`. Give the workspace, backend, and frontend distinct Validator marker/config files and make the fake PR client return distinct URLs while recording cwd and arguments.
- Journey: Launch Agent Runner from `foo`; execute workspace planning, backend tasks and repository lifecycle, frontend tasks and repository lifecycle, then workspace completion. Inspect repository contents, process logs, the workspace run directory, state, audit, captures, and saved run model.
- Assertions: Planning and shared artifacts are committed under `foo`; backend completes all numbered tasks and validation before frontend begins; every process sees the correct built-ins and cwd; each scope's Validator marker is used; docs is untouched; repository captures and fixed-name evidence do not cross scopes; state and audit live under the workspace identity; one workspace and two implementation PR operations and URLs are recorded in the defined order; and the run completes successfully.
- Execution: Add a POSIX `cmd/agent-runner` E2E using the existing build-and-fake-executable harness; run in the normal `go test ./...` CI job.

### E2E-002: Failed repository resumes without replay or rerouting
- Covers: Sequential fail-fast execution, recursive repository state, root-keyed process-boundary resume, completed-repository skipping, pending repositories, configuration/task-group drift rejection, and cross-run checkout locking.
- Surface: Built `agent-runner` CLI across an initial run and separate `--resume` process invocations.
- Setup: Reuse the Git-backed workspace shape with three selected implementation repositories. A controlled executable writes durable invocation markers, completes backend, fails once in a nested frontend task, and would expose any premature or repeated work. Preserve the generated run directory. Prepare isolated copies that modify the selected order, configured root, and task-group ownership before resume.
- Journey: Run until frontend fails, inspect the persisted state, attempt an overlapping second run while the first process is alive, resume the unchanged failed run from the workspace root to completion, then attempt resume against each drifted copy and from a workspace subdirectory.
- Assertions: The first process never starts the third repository; the overlapping run fails before checkout mutation; valid resume does not rerun backend or completed frontend tasks, resumes frontend at the retained nested point, and starts the third repository only after frontend succeeds; each drifted resume fails before running a command and identifies the mismatched repository or plan identity; and a subdirectory invocation is rejected rather than creating a second run bucket.
- Execution: Add a process-level `cmd/agent-runner` E2E beside the headless smoke tests; run in the normal `go test ./...` CI job.

### E2E-003: Terminal run views expose repository hierarchy
- Covers: Live repository visibility, auto-follow, failure focus, historical reconstruction, navigation, output isolation, completion summaries, ordered PR breadcrumbs, and implicit single-repository presentation.
- Surface: Public live-run and `--inspect` terminal interfaces driven through a PTY and reconstructed with a terminal emulator.
- Setup: Launch a deterministic slow fixture run with workspace steps and two repositories so the controller can observe transitions. Record different output, usage, and PR URLs per repository. Prepare a completed implicit-single-repository run as a control. Use the existing PTY test infrastructure and terminal-screen reconstruction rather than raw differential repaint bytes.
- Journey: Observe backend start/completion and frontend activation live; pause and restore auto-follow; select and drill into each repository; open the summary; finish the run; reopen it through `--inspect`; then inspect the implicit control run.
- Assertions: Screens show exactly one additional name-only repository level; focus follows the deepest active child and lands on nested failure; manual navigation is stable; repository detail/output and summary totals are isolated; breadcrumbs retain independently linked comma-separated PR labels; saved inspection matches live hierarchy; and the implicit control has no repository row.
- Execution: Add a POSIX PTY E2E under `cmd/agent-runner`; run in the normal `go test ./...` CI job with a bounded timeout.

## Agent Acceptance Tests

### AT-001: Real OpenSpec multi-repository mechanics across temporary GitHub repositories
- Classification: Required
- Covers: Git-backed OpenSpec workspace behavior, shipped OpenSpec implementation/archive/finalization building blocks, ordered task groups, repository preflight and Validator configuration, contiguous implementation, inherited workspace lead session, isolated evidence aggregation, acceptance-phase repository remediation, workspace archive/PR, per-repository draft and final PR handling, and live/saved repository presentation.
- Actor and surface: Acceptance tester operating a non-interactive acceptance workflow that composes the shipped OpenSpec workspace, repository implementation, remediation, archive, and finalization building blocks through Agent Runner's public CLI, then inspecting the resulting GitHub pull requests and run views. Interactive top-level definition/review is reserved for HT-001.
- Setup: Require authenticated real-agent credentials, an authenticated `gh` session authorized to create private repositories, push branches, create/update/close pull requests, and delete repositories, plus Agent Validator and OpenSpec. Before any mutation, record three exact randomized repository names under the authenticated owner: workspace, backend, and frontend. Create all three private. Clone the workspace as `foo`, clone backend and frontend as ignored nested repositories, seed distinct Validator configurations and minimal projects in all three, create feature branches, configure backend and frontend in `foo/.agent-runner/config.yaml`, and preseed an approved shared OpenSpec change with strict backend/frontend task groups. Include one acceptance finding whose approved fix is owned only by backend.
- Steps: From `foo`, invoke the current Agent Runner source through the non-interactive acceptance workflow. Observe repository implementation, Validator, draft PRs, workspace evidence aggregation, backend-only remediation and re-verification, OpenSpec archive, workspace finalization, and implementation-repository finalization. Inspect all three repositories, the OpenSpec artifacts, `state.json`, `audit.log`, session identities, isolated Validator evidence, remediation evidence, all three GitHub pull requests, the saved run detail, and the completion summary.
- Expected: The workspace owns and versions the OpenSpec artifacts and owns the run artifacts; backend finishes before frontend starts; each implementation repository uses only its tasks and Validator configuration; the workspace-instantiated named lead session is reused with explicit current-repository context; the acceptance fix changes, validates, commits, pushes, and re-verifies only backend; the workspace and both implementation repositories have intended commits and independently finalized PRs; the run shows name-only implementation-repository containers and workspace-first ordered PR links; workspace aggregation/archive runs once; and no repository identity, capture, evidence, output, metric, or session leaks into its sibling.
- Evidence: Capture terminal screenshots of live backend and frontend states, saved repository drill-down, completion summary, and breadcrumb PR links; retain the final normalized task index, relevant state and audit excerpts, named-session IDs, isolated Validator reports, commit SHAs, and all three PR URLs before cleanup.
- Effects and cleanup: Authorized effects are exactly three recorded temporary private repositories, real agent/API usage, pushes, CI runs, and pull requests. Do not merge the PRs. Preserve the repositories only when AT-002 and HT-001 will immediately reuse them on fresh branches or isolated worktrees. On every other AT-001 terminal path, retain precise failure evidence, close acceptance PRs if needed, delete exactly the three recorded repositories, verify their names no longer resolve, and remove only the acceptance-created local parent directory.
- Permitted substitutes: None. Local repositories, mocked `gh`, dry runs, or omitted PR finalization do not satisfy this required acceptance flow.

### AT-002: Real spec-driven simple mechanics and exact repository cleanup
- Classification: Required
- Covers: Spec-driven workspace artifacts, shipped simple implementation/finalization building blocks, compact multi-repository task groups, repository-contiguous implementation and validation, non-interactive flow evidence, independent finalization, implicit monolithic-plan compatibility, and cleanup of authorized external effects.
- Actor and surface: Acceptance tester operating a non-interactive acceptance workflow that composes the shipped simple-change implementation, evidence, remediation, and finalization building blocks through Agent Runner's public CLI, then verifying and cleaning the exact temporary GitHub resources created for acceptance. Interactive top-level planning/review is reserved for HT-001.
- Setup: Reuse only the three exact repositories recorded for AT-001. Return each clone to its default branch, ensure AT-001 changes are not implicitly incorporated, and create fresh feature branches. Place the external spec-driven change directory outside tracked workspace contents, keep the same repository configuration and distinct Validator setups, and choose a minimal change with one compact task group per implementation repository.
- Steps: From `foo`, run the non-interactive simple acceptance workflow against a preseeded grouped plan. Allow both repository implementations and validations to complete, produce workspace-level flow evidence, apply any preapproved repository remediation, and finalize an independent PR for each implementation branch without creating a workspace PR. Also run the parser and implementation-input boundary against an isolated implicit monolithic `tasks.md` fixture. Inspect the live and saved run views, repository histories, Validator evidence, external planning artifacts, and PR states. After HT-001 is complete, close remaining acceptance PRs if necessary, delete exactly the three recorded private GitHub repositories, verify all three remote names no longer resolve, and remove only the acceptance-created local parent directory.
- Expected: The simple workflow uses the same repository order and isolation without a separate workflow flavor; compact task groups route correctly; each implementation repository validates and finalizes independently; workspace review runs once; external planning artifacts remain outside tracked workspace contents; the clean workspace produces no new PR; presentation matches the full workflow; and all exact temporary remote and local resources are removed after evidence capture.
- Evidence: Capture terminal screenshots of both repository containers and final summary, the external task-group index, state/audit excerpts, Validator reports, commit SHAs, five acceptance PR URLs across both flows, and `gh` evidence that the three exact repositories no longer exist after deletion. Record the cleanup commands and their outcomes with secrets removed.
- Effects and cleanup: Authorized effects are fresh branches, real agent/API usage, CI, and two additional PRs in the already recorded temporary repositories, followed by closing PRs and deleting those exact repositories. Never enumerate and bulk-delete by prefix. Cleanup failure is an acceptance impediment and must be reported with the still-existing exact URLs; it must not be hidden behind an otherwise successful result.
- Permitted substitutes: None for real agents, Validator, independent PRs, or exact cleanup. The non-interactive composition is intentional; HT-001 separately covers the interactive top-level workflow surface.

## Human-Only Testing

### HT-001: Interactive top-level change workflow handoff
- Reason: The real `openspec:change` and `spec-driven:simple-change` workflows contain interactive agent steps that inherit a human terminal. Repository instructions state that an agent-controlled synthetic PTY cannot launch runs or conduct the required real conversation, so claiming autonomous coverage would be false.
- Prerequisites: A human at a real terminal; the built current Agent Runner source; the Git-backed workspace and implementation repositories prepared for AT-001/AT-002 before cleanup; authenticated agent, OpenSpec, Validator, and `gh` access; fresh branches or isolated local copies.
- Instructions: Launch each real top-level workflow from the canonical workspace root. Conduct its definition/planning and review conversations through the point where the approved repository set and grouped task artifacts are validated. Confirm the OpenSpec flow writes workspace-owned artifacts, the simple flow writes its external artifacts, both show the expected workspace-level steps and repository transition, and neither requires typing the implicit name `default`. The human may stop before repeating the autonomous implementation/PR mechanics already proven by AT-001/AT-002. Preserve terminal screenshots and the resulting planning artifacts, then allow AT-002 cleanup to delete only the exact recorded resources.
- Required decision or observation: Confirm that both shipped top-level interactive workflows can be started and guided naturally from the workspace root, derive the intended repository order without a multi-repository workflow variant, and reach the repository execution boundary with no incorrect cwd, missing parameter, or terminal-handoff behavior.
