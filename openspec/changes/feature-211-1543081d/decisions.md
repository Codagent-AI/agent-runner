# Decisions

## propose

- **Verdict: go.** The factory (agent-factory#92) is blocked on this, Paul ruled out log parsing, and the evidence needed to classify crashes already exists in the agent executor. Alternatives considered: no-go with factory-side log parsing (rejected by Paul on 2026-10-04). Decision-bearing: yes.
- **Represent the classification as a failure kind next to the `failed` outcome, not as a new outcome value.** Alternatives considered: a new `StepOutcome` such as `infrastructure_failed` (rejected: every flow-control, warning, TUI, and audit consumer would need to treat it as failed anyway, and it changes the value of an existing persisted field). Decision-bearing: yes.
- **What counts as a crash:** launch failure, non-zero headless exit after adapter filtering, a kill not initiated by the runner, and runner invocation errors mid-session. Excluded: pre-launch definition/config errors, sessions that finished but were judged failed (AskUserQuestion, uncollected agent calls), and user aborts. Alternatives considered: treat every failed agent step as infrastructure (rejected: deterministic config errors would retry forever); detect specific provider error strings (rejected: brittle, and it is the log parsing Paul ruled out). Decision-bearing: yes.
- **Repair agents are covered.** agent-factory#92's decision lists repair agents among the steps whose crash is technical. Alternatives considered: workflow agent steps only. Decision-bearing: no (follows the issue context).
- *(Superseded by PR-001 below.)* **A container is an infrastructure failure when the failure that ended it was one, or when it absorbed a crash with `continue_on_failure` earlier in the same execution and still ended failed or exhausted.** Alternatives considered: propagate only the terminating failure (rejected: builtins such as `finalize-pr` absorb `wait-ci` agent failures, so a crash would resurface as a red CI gate, contradicting "a red result after an agent that finished stays failed"); make `continue_on_failure` refuse to absorb crashes (rejected: changes existing flow-control semantics for all workflows). Decision-bearing: yes.
- **Expose the kind to the calling workflow through a built-in variable for the preceding step**, scoped like `skip_if: previous_success`, plus durable audit/state fields and `run_end`. Alternatives considered: a new `skip_if` keyword only (less flexible); a distinct process exit code (changes a public interface; the factory already treats a failed run as technical). Exact variable name left to the spec. Decision-bearing: no.
- **Out of scope: shell/script failures, `call_agent` children, in-runner retries, factory workflow edits.** Decision-bearing: no.

## proposal-review

- **PR-001 (structural) — applied.** A recovered, successful container erased an absorbed crash, so the factory could not apply "any crash is technical". Added a separate, sticky **crash-observed** signal. It propagates through successful and failed groups, loops, and sub-workflows. It is exposed to the caller through a built-in variable and on `run_end`, and nothing within an execution clears it. On resume, a re-executed step's signal is replaced and signals from completed steps are kept. **Supersedes** the earlier propose decision that tainted a failed container's failure kind with absorbed crashes: the failure kind now describes only the terminating failure, and absorbed crashes are carried by the crash-observed signal. Alternatives considered: keep the taint rule only (rejected: misses recovered successes); make an absorbed crash fail the container (rejected: changes `continue_on_failure` and outcome semantics for every workflow, and the policy belongs to the caller). Not direction-level: the outcome is unchanged and the new fields are additive, so it stays within the issue's "report the crash, pass it up". Decision-bearing: yes.
- **PR-002 (significant) — applied.** The run failure reason comes from `LastFailure`, which only shell and script checks write, so a direct agent crash had no reason source and could pick up stale check evidence. Added a durable agent-crash **failure origin** (step ID, audit prefix and scope, attempt, bounded error or stderr). `classifyRunFailure` prefers it when the terminating failure kind is infrastructure and keeps check evidence otherwise. A later terminating failure replaces the origin, a step's success clears its own origin, and resume keeps earlier origins for inspection. Alternatives considered: write agent crashes into `LastFailure` (rejected: that record's guarded-execution semantics are specific to checks, and mixing the two would blur check evidence). Decision-bearing: yes.

## spec

- **Failure kind values are `infrastructure` and `step`.** The kind is present only for `failed` and `exhausted` outcomes. Alternatives considered: `crash`/`ordinary`, or a boolean `infrastructure_failure` (rejected: a boolean cannot distinguish "not failed" from "ordinary failure" on end events). Decision-bearing: no.
- **Built-in variables are named `{{last_step_failure_kind}}` (`infrastructure` | `step` | empty) and `{{last_step_crash_observed}}` (`true` | `false`).** They are always present, they track the same preceding step that `skip_if: previous_success` evaluates (skip handling follows each scope's existing tracker; see RA-002 below), and they follow normal built-in precedence. Alternatives considered: a `skip_if` keyword (less flexible); omitting the variables when empty (rejected: that makes `sh:` expressions fail interpolation on the first step). Decision-bearing: no.
- **Crash boundaries.** These count as infrastructure: launch failure, a non-zero headless exit after the adapter filter, a kill by an external signal, and runner control-channel or durability failures. These are `step`: errors before the invocation starts, a disallowed AskUserQuestion, and uncollected agent calls. A `call_agent` child crash neither classifies its parent nor sets its parent's crash-observed signal. User aborts, Ctrl-C, and an interactive session the user exits without a continue trigger stay `aborted`. Alternatives considered: count child-call crashes (rejected: out of scope in the proposal, and the parent finished and decided what to do with the tool result). Decision-bearing: yes.
- **Loop exhaustion kind.** An exhausted loop takes the kind of its last iteration's terminating failure, or `step` when that iteration ended without a failure (for example, a `break_if: success` loop whose gate failed under `continue_on_failure`). Alternatives considered: `infrastructure` if any iteration crashed (rejected: the crash-observed signal covers that). Decision-bearing: no.
- **Repair cycle kind.** A crashed repair agent still counts as a failed attempt (existing behavior, and the check is not rerun). The check's terminal kind is `infrastructure` only when the attempt that ended the cycle failed by crash; a red recheck after a repair agent that finished, or a blocked declaration, is `step`. Crash-observed is set either way. Decision-bearing: no.
- **Resume.** A re-executed step's signals come from its new execution. Signals from completed children are persisted and combined into a re-entered container. Runs written before this change read as kind `step` and crash-observed false. A run whose crash stopped it and then succeeded on resume reports crash-observed false for the re-executed step. This matches a retried crash being recovered. Decision-bearing: yes.
- **Audit fields: `failure_kind`, `crash_observed`, `failure_origin`.** They go on `step_end`, `iteration_end`, `sub_workflow_end`, and `run_end`, and are additive, with `outcome` unchanged. They are specified as a new requirement instead of modifying "End event data", so existing consumers keep their contract. Decision-bearing: no.
- **Failure reason format** is `<step-id> failed (infrastructure): <first non-empty error/stderr line>`. When there is no text, the exit code is used, or `agent session did not finish`. ` after N repair attempts` is appended when a crash ends a repair cycle. The origin's excerpt size and the persisted layout are deferred to design. Decision-bearing: no.

## design

- **Classify at the invocation boundary.** `runAgentProcess` and `InvokeAgent` return a `Crashed` flag, and `ExecuteAgentStep` records crashes through a single `recordAgentCrash` helper. Agent calls ignore the flag. Alternatives considered: classify in `emitAgentEnd` from exit code and error after the fact (rejected: the cancellation cause, the stall cause, and the pre-start vs. post-start distinction are lost by then). Decision-bearing: no.
- **The terminating failure kind travels through a reset-per-dispatch `ctx.StepFailure` side channel.** Every failure defaults to `step`, and containers copy their blocking child's value and clear it when they absorb a failure. Alternatives considered: change every executor to return a `StepResult` struct (rejected: very wide churn across executors, runner, repair, and tests for no behavioral gain). The side channel mirrors the existing `LastStepOutcome` and `LastFailure` patterns, and the default to `step` fails safe. Decision-bearing: yes.
- **Crash-observed is derived from a run-scoped, persisted `CrashLedger` queried by structured nesting path.** Alternatives considered: explicit per-container OR-propagation with accumulators persisted in `NestedStepState` (rejected: needs code in every container plus resume plumbing); string-prefix matching on audit prefixes (rejected: `loop:2` does not prefix-match `loop`). Decision-bearing: yes.
- **Resume pruning is leaf-only and keyed on execution session.** When an agent or check step starts, records at or under its path from other execution sessions are removed. Containers never prune. This satisfies "re-executed steps reflect their new execution" without erasing in-run replay crashes or the crashes of completed children. Decision-bearing: no.
- **Spec amendments revealed by design:**
  - A Cursor result-stall termination and an `ErrWaitDelay` exit without completed output count as infrastructure.
  - A run-stop cancellation does not count as infrastructure.
  - The terminal-handoff (suspend-hook) failure is listed under runner machinery.
  - The excerpt bound is 4 KiB (2 KiB head and 2 KiB tail) and includes the error message.
  - The origin lifecycle is reworded: origins stay inspectable on their end events, and the terminating origin is selected only when the run's failure kind is `infrastructure`. This replaces "a successful step clears its origin", which conflicted with sticky crash observation across rerun replays.
  - An inline repair agent's reason uses `<check> repair` as the step ID.

  These are technical implications within the approved behavior, not direction changes. Decision-bearing: yes.
- **`state.json` mirrors `failure_kind`, `crash_observed`, and the crash ledger**, so consumers can classify a finished run without the audit log. Alternatives considered: `run_end` only (rejected: the factory reads run state). Decision-bearing: no.
- **Stdout-only provider errors (Claude stream-JSON) degrade the reason to `exit code N`**, while the classification stays correct. Adding an adapter hook to extract the message is deferred. Decision-bearing: no.

## test-plan

- **Four integration obligations, two end-to-end.**
  - The integration obligations are: real subprocess terminations through both production process runners (INT-001); the real builtin `implement-task` (INT-002) and `finalize-pr` (INT-003) carrying the signals; and a crashed repair agent through the runner's failure reason (INT-004).
  - The end-to-end obligations run the built binary: a crash inside a sub-workflow stops the run (E2E-001), and a run resumes after a crash or recovers in a later loop iteration (E2E-002).
  - Alternatives considered: E2E for every builtin (rejected: the builtins' flow control is proven more cheaply in `internal/exec` with the real YAML); no INT for the process runners (rejected: the classification depends on how real `os/exec` reports signals, wait delays, and cancellation, which a fake `ProcessRunner` cannot prove).

  Decision-bearing: no.
- **Acceptance envelope.**
  - Allowed: isolated HOME, fake CLIs as the primary crash source, and at most a few real-CLI invocations that fail before model work, to observe real exit and stderr shapes.
  - Forbidden: GitHub remotes, the live factory, Paul's run history, and successful real-model sessions.

  Alternatives considered: allow real agent sessions (rejected: real cost, and a crash cannot be reliably induced through them). Decision-bearing: no.
- **No human-only testing.** Every obligation is observable by an agent with fake CLIs and a temp HOME. Decision-bearing: no.

## approach-review

- **RA-001 (high) — applied.** The preceding-step outcome, failure kind, and crash-observed value now move together in one `PreviousStep` tracker per scope. It is persisted in `NestedStepState.PreviousStep` (root, sub-workflow, and iteration entries) and restored when resume re-enters the scope. This adds the `step-flow-control` requirement "Preceding-step tracking survives resume", a resume scenario in `infrastructure-failure-classification`, design §2 and Decision 8, and INT-005. It also fixes a pre-existing gap: `skip_if: previous_success` saw nil after resume, contrary to its spec. Runs without the field resume as they do today. Alternatives considered: persist only the new signals (rejected: they would drift from the outcome `skip_if` reads). Not direction-level: it is additive state and makes resume consistent with the existing spec. Decision-bearing: yes.
- **RA-002 (medium) — applied.** The variables follow each scope's existing skip behavior. Groups and loop bodies record the skipped step, so the variables become empty and `false`. Top-level and sub-workflow sequencers keep the last executed step. I added the `builtin-vars` requirement "Last-step variables follow each scope's skip tracking" with four per-scope scenarios, corrected design §2, corrected the spec-step decision text, and added skip-synchronization tests. Alternatives considered: make skip handling uniform (rejected: it changes existing flow control for all workflows). Decision-bearing: yes.
- **RA-003 (medium) — applied.** Orchestration errors are `step` with no origin. A top-level stop that does not come from a dispatched step's failure (a `skip_if` evaluation error, a resume-resolution or replay-priming error) explicitly sets `StepFailure{Kind: step}`, so an earlier absorbed crash cannot become the run's failure kind or origin. Its crash still shows in `crash_observed`. I added a spec sentence and scenario to "Container failure kind", an `audit-log-entries` scenario, the design §2 rule, and a runner test. Decision-bearing: no.
- **RA-004 (low) — applied.** The stderr excerpt is at most 4096 bytes in total, including a fixed marker. The bytes left after the marker are split with the head getting half rounded down and the tail the rest, with cuts moved inward to UTF-8 boundaries. I updated `run-failure-evidence` with a bounded-stderr scenario, design §3 (excerpt rule), Decision 5, and the tests. Decision-bearing: no.
